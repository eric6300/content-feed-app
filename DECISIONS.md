## 2026-09-12 — Weather and service cards chosen as the second and third source types

**Considered:** The product requirements' suggestions for a second/third card type — a trending-movies source (TMDB) alongside weather (Open-Meteo) — vs. dropping the movie type and using a service-card shape (DummyJSON, seeded locally) instead, and whether to add a third type at all when the requirements only require two.
**Decided:** Keep weather live (Open-Meteo, no key, matches the requirements' example of a stable keyless source). Drop TMDB — it requires a registered API key, which adds setup friction — and use a service-card shape seeded from DummyJSON instead, interspersed into the paginated article stream every 5 articles rather than as a one-time carousel, closer to the functional reference of a single promotional card between articles. Ship three source types rather than the minimum two, to show fuller heterogeneity than required.
**Trade-off:** Mocking service cards trades away a second live-network demonstration, but articles and weather stay live specifically so the app still shows real networking, pagination, and error/loading handling — mocking all three sources was considered and rejected for removing that entirely. TMDB setup friction, not a preference for mocking, is what moved the third slot to a local source.

## 2026-09-12 — Freshness/caching: key+TTL `FreshnessGate`, not an RxCache-style generic cache

**Considered:** (1) An RxCache-style generic cache — annotate/wrap each API call with a TTL, library transparently serializes and stores the response on disk. (2) A `FreshnessSource` enum (`WEATHER`, `ARTICLES`, ...) each carrying its own TTL constant, checked via a shared timestamp store. (3) A `FreshnessGate` keyed by a plain string + `Duration`, storing only a last-fetched timestamp per key in DataStore Preferences, with Room remaining the sole store for the actual cached data.
**Decided:** Option 3. Only two live sources need TTL freshness (weather 15 min, articles 1 hour), so a generic annotation/disk-serialization framework solves a "many heterogeneous API call sites" problem that doesn't exist here — and RxCache is also RxJava-based and unmaintained. It would also duplicate storage: Room is already the source of truth for weather/article rows, so a second cache means two stores to keep in sync; the one thing Room doesn't give for free — "when was this last fetched" — is the only piece worth extracting. An initial `FreshnessSource` enum draft was rejected because every new source would mean editing a shared file. Final shape: a plain string key + `Duration` TTL, paired with a `refreshIfStale(key, ttl, fetch, persist)` extension that collapses each repository's check-refetch-persist-mark cycle into one call.
**Trade-off:** Less "batteries included" than a generic caching library — no automatic request-signature hashing, disk serialization, or annotation processor. But adding a new live source later costs zero changes to shared files, and there's only one cache store (Room) instead of two.

## 2026-09-13 — Baseline stack carried over from prior work, not evaluated in this project

**Considered:** Evaluating each core technology from first principles for this project — Compose vs. the View system, MVI vs. MVVM, Koin vs. Hilt/Dagger vs. manual DI, Room vs. SQLDelight vs. raw SQLite, coroutines/Flow vs. RxJava — versus adopting the stack already in daily use and spending the implementation effort on product behavior instead.
**Decided:** Adopt the established stack: Kotlin + Jetpack Compose with Material 3; MVI with a `State`/`Event`/`Effect` contract per screen; Koin for DI; Room as the content store with DataStore Preferences for freshness timestamps; coroutines + Flow/StateFlow as the concurrency model. Each item was checked for feasibility on this project's toolchain — actual dependency resolution, compilation, and lint — rather than compared against an alternative. The only substitution was Realm → Room. This entry is deliberately not written as a comparison, because no comparison took place.
**Trade-off:** There is no in-project evidence that any of these is the best fit for this problem, and carrying a familiar stack risks carrying a habit that does not suit the task. In exchange, comparison overhead was kept low and the time went into the feed composition, freshness, and offline behavior instead — where the product requirements actually are. The two entries below are where this project's own constraints genuinely forced a choice.
**Retrospective (written at release, not a decision record):** Compose — greenfield app, and the feed's per-item state variance suits a declarative list better than adapter-based views. MVI — the feed carries several simultaneous per-source states, so one reduced state object is easier to reason about than scattered `LiveData`. Koin — no code generation, so build times stay low on a small project; Hilt's compile-time graph validation would matter more on a larger team. Room — a relational store is required anyway for the retention query and the placement join. Coroutines/Flow — Room and DataStore both expose `Flow` natively, so anything else means adapters at every boundary.

## 2026-09-13 — Room is the single source of truth; freshness timestamps live in DataStore

**Considered:** Keeping everything in one store — either last-fetched timestamps as columns in Room next to the rows they describe, or deriving "when did we last check" from `max(ArticleEntity.fetchedAt)` — versus splitting responsibilities: Room for content, DataStore Preferences for freshness timestamps.
**Decided:** Split. A successful fetch upserts into Room; the UI and ViewModels read only Room DAO `Flow`s and never see Retrofit, `ApiResponse`, or DTO types, which stop at `RemoteDataSource`. The freshness timestamp is a switch that triggers the write path, not data the user reads, so it belongs in DataStore rather than beside the content. Deriving it from `fetchedAt` was specifically rejected: pagination writes rows too, so scroll-driven loads would pollute the freshness signal and cause refetches at the wrong times.
**Trade-off:** Two stores to reason about instead of one, and a read/write asymmetry every new source has to respect. In return, cache-first startup falls out for free rather than being implemented: because the UI only ever observes Room, "show cached content immediately, check freshness in the background, update in place if it changed" needs no explicit refresh-the-screen step.

## 2026-09-16 — The repository mutex covers the local read/write section, not the network call

**Considered:** (1) No synchronization — a code review found a real collision: `refreshTop` (reconnect-triggered) and `loadNextPage` (scroll-triggered) reach the same singleton repository concurrently and can corrupt `FeedPlacementDao`'s `MAX+1` pool-index and assignment-sequence counters, or silently swallow one side's pagination cursor progress. (2) One `Mutex` around the whole method, including the network fetch. (3) A `Mutex` around only the local read/write section, with the fetch left outside it.
**Decided:** Option 3. The lock wraps `persistTopPage`'s Room upsert, placement assignment, and cursor read/write, the `RemoteResult.Loaded` branch of `loadNextPage`, and all of `pruneStaleUnsavedArticles`. The cursor write also changed from absolute (`offset + page.articles.size`, read before the network call) to an in-lock relative read — the absolute write was the actual bug, since a concurrent `refreshTop` committing progress during the fetch gets silently overwritten. `SourceRefresher` deliberately does the opposite and holds its lock across the fetch: the unit being protected there is a whole refresh attempt, to stop reconnect and foreground checks both passing the stale check and firing duplicate requests.
**Trade-off:** Option 2 was rejected as worse than the bug it fixes — holding a lock across a network round trip lets a stalled reconnect fetch block the user's scrolling. The accepted cost is that the two coroutines briefly block each other on local database and DataStore writes, which are bounded and in-memory. Verified empirically: a fake `FeedCursorStore` holding a real `var offset: Int` plus a `CompletableDeferred`-gated fake remote source forces the exact interleaving, and the production code was temporarily reverted to the pre-fix logic to confirm both new tests actually fail before restoring it. The pre-existing tests used `mockk(relaxed = true)` with `flowOf(...)` and are structurally incapable of catching this class of bug.
